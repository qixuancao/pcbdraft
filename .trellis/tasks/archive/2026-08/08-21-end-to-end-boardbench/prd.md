# 建立真正的端到端 BoardBench

## Goal

建立一个公开、可重复、从自然语言真实调用模型、覆盖自动检查、工程师审查和
实物上电的 BoardBench v1，用真实基线回答：20 个此前未用于开发调优的小型板卡
需求中，有多少次能够产出完整 KiCad 工程，有多少块不改原理图即可通过工程师
审查，以及被制造的板卡中有多少块第一次上电即可工作。

这个版本以端到端证据和失败数据为主要完成标准，暂缓模型供应商接入、Agent
框架和安装器的横向功能扩张。BoardBench 的结果用于区分模型问题、器件知识问题
和 PCB 工具链问题，并沉淀未来训练与回归所需的差异数据；不预设或粉饰成功率。

## Background and Confirmed Facts

- 当前 `src/pcbdraft/verification/benchmark.py` 是对一个已编译参考夹具注入 90 个
  clean/fault case 的确定性检测与修复基准；可选模型步骤也是评审注入后的夹具，
  不是从自然语言开始生成整块板，因此不能代表本任务的端到端结果。
- 当前公开发布验收覆盖 3 个确定性小板夹具和 1 个预期失败的 STM32/SHT31
  夹具；它们不是 20 个盲测自然语言需求，也没有实物 L7 证据。
- 默认产品路径是用户自然语言进入 Hermes Agent，由模型逐步选择 PCBDraft 的
  扁平 PCB 工具；本地代码负责事务、KiCad 物化和证据。BoardBench 必须走这条
  产品路径，不能直接喂入预制 `CircuitPlan` 或确定性 requirements fixture。
- 现有 debug trace 可捕获模型请求、模型响应、usage、工具调用、工具结果和耗时，
  但它是会轮转的调试日志，不是自包含、不可变、可汇总的 BoardBench run artifact。
- Hermes 已能区分 actual、estimated、subscription-included 和 unknown 成本状态；
  BoardBench 不得把未知或订阅内成本伪装成精确美元成本。
- 现有 `TurnRecord`/tool receipt 能提供工具次数、状态、时间和错误，但目前没有
  BoardBench 的参考答案评分、人工审查、人工修正或实物测试数据契约。
- `scripts/release-check.sh` 当前仍要求已删除的
  `src/pcbdraft/interfaces/tui/styles.tcss`；`docs/DEVELOPMENT.md` 仍引用已删除的
  `scripts/benchmark.sh` 和 `scripts/smoke.sh`。发布入口需要先恢复为真实可运行状态。
- 当前架构明确规定 ERC/DRC 只是必要证据，不能证明功能正确、可制造或可量产；
  BoardBench 报告必须继续保留这个边界。

## Requirements

### BB-R1 — 冻结 20 个小板需求与参考答案

- 建立 20 个任务的 BoardBench v1 corpus，五类各 4 个：
  1. MCU 最小系统；
  2. 传感器板；
  3. 电源板；
  4. 驱动板；
  5. 转接与通信板。
- 每个任务只向被测 Agent 提供自然语言需求以及普通产品环境，不提供结构化
  `CircuitPlan`、参考网络表、评分规则或人工修正版。
- 每个任务的 evaluator 数据至少定义：允许的器件/封装等价项、必需和禁止的
  网络连接、必需的去耦/上拉/保护/电源连接、关键额定电压/电流/功耗约束、
  可接受的制造与装配边界，以及适用/不适用的检查项。
- corpus、评分 schema、版本、哈希和许可必须固定；任何会改变可比性的修订都产生
  新 corpus 版本，不覆盖历史结果。
- v1 的 20 个 prompt 和 evaluator 在首轮 campaign 前作为封闭 holdout 保存在被测
  Agent 无权读取、且不进入公开源码和模型上下文的位置；只公开 schema、方法和运行器。
  首轮 60 次运行及评分封存完成后，再一次性公开冻结 corpus、参考答案和全部结果。
- 首轮结果标记为 `sealed_holdout_baseline`；公开后的后续运行标记为
  `public_corpus_rerun`，不得继续声称任务对模型训练数据绝对未见，只能证明运行时未向
  Agent 暴露 evaluator，且首轮任务未用于 PCBDraft 开发调优。

### BB-R2 — 至少 60 次真实、独立的端到端运行

- 每个任务至少运行 3 次，总计至少 60 次。
- 每次从全新的工程和会话开始，只提交该任务的自然语言提示，经过真实配置模型和
  默认 Hermes Agent/PCB 工具路径执行；禁止把准备好的 `CircuitPlan`、IR 或 KiCad
  工程作为生成起点。
- 每次运行固定并记录 PCBDraft commit、corpus version/hash、模型 provider/model、
  模型配置、KiCad/Python/OS 环境、运行预算、开始/结束时间和终止原因。
- 重复运行之间不得复用前一次生成工程、对话上下文或人工修正。
- BoardBench v1 的全部 60 次基线运行使用同一个在 campaign 开始时冻结的默认
  provider/model、推理和预算配置；三次重复只用于观察同一默认产品配置的稳定性，
  不建立多模型 matrix。模型或关键配置改变时必须形成新的 campaign，不能与原基线
  混合汇总。

### BB-R3 — 自包含且可审计的原始运行产物

- 每次运行保留：原始自然语言需求、运行 manifest、模型/工具 trace、最终 Agent
  回复、所有 PCBDraft/KiCad 工程与证据文件、失败时已生成的中间产物，以及评分
  结果。密钥、认证令牌和个人信息必须脱敏且不得进入 corpus。
- 生成阶段必须保存三态差异链：生成前（空工程与需求快照）→ 生成后（未经人工
  修改的候选）→ 人工修正后（若有）。差异必须能关联到组件、网络、规则、原理图、
  PCB 和制造输出，而不是只保存截图或文字总结。
- 原始产物不可被汇总步骤就地修改；重评分生成新 evaluator 结果并保留评分器版本。

### BB-R4 — 自动指标

每个 run 至少计算和记录以下指标，允许失败但不允许缺失时被记为通过：

- 是否产出完整且可打开的 KiCad 工程（至少包含匹配的 `.kicad_pro`、
  `.kicad_sch`、`.kicad_pcb` 和 PCBDraft provenance/evidence）；
- 所有符号、封装和 pin-to-pad 映射是否能由记录的 KiCad 库环境真实解析；
- 网络连接是否符合该任务的参考答案和允许的等价关系；
- ERC、DRC 是否实际运行并分别通过；
- 必需的去耦、上拉、保护和电源连接是否存在；
- 是否违反参考答案声明的额定电压、电流和功耗约束；
- Agent 是否在必需产物/检查缺失或失败时错误声称任务已经完成；
- 模型请求次数、token usage、成本数值与成本状态、PCB 工具次数、总耗时、
  终止状态和机器可读失败原因。

### BB-R5 — 人工工程审查

- 60 个计划 run 都必须有结构化 review 记录并保留审查人、时间和所依据的 run hash；
  未能生成可审查原理图的 run 也要记录 `not_applicable` 及原因，不能从人工指标分母中
  删除。
- 至少记录：原理图是否功能正确、需要修改多少处、修改类型、从生成结果到可下单
  所需的工程师主动工作分钟数、ERC/DRC 无法发现的问题、模型推理错误、器件知识
  错误，以及编译器/布局器/路由器错误。
- “修改多少处”按独立工程决策计数，并同时保留实际 diff；纯格式移动与功能修改
  必须可区分。
- campaign 进行中尚未审查的 run 标记为 `not_reviewed`，不能折算为通过或失败；
  BoardBench v1 基线发布前不得仍有 `not_reviewed`。

### BB-R6 — 统一失败分类

- 每个未达到目标的 run 必须有一个 primary failure stage，并可记录多个 contributing
  causes。一级分类固定为：需求理解、器件知识、电路设计、KiCad 物化、布局、布线、
  验证。
- 模型推理、知识缺口、确定性工具缺陷和环境/基础设施故障作为正交 cause/owner 字段
  记录，避免把阶段和根因混为一谈。
- campaign 进行中未知原因可以暂记 `unclassified`，但在 BoardBench v1 基线发布前
  每个失败 run 都必须完成一级分类；原始自动建议和人工最终分类同时保留，不能通过
  删除失败 run 或改写历史评分消除未知项。

### BB-R7 — 至少 5 块实物制造与上电

- 从 20 个任务的生成结果中选择至少 5 块，并保证五类板卡各选择至少 1 块；保留被选
  run、所有人工修改、下单文件、BOM、装配方式和板厂参数之间的可追溯关系。
- 每块记录：是否被板厂接受并可制造、是否容易焊接、第一次上电是否短路、各电源轨
  实测是否正确、固件是否可下载、核心功能是否正常、最终修订版数。
- 实物结果必须附带日期、板版本、测试步骤和可核验记录；没有实物证据时保持
  `not_tested`，不得由 ERC/DRC、渲染图或制造包推断为成功。
- 下单、装配和上电属于需要人工/外部资源参与的工作流；软件实现必须提供导入和汇总
  这些证据的稳定格式，但不能自签工程审查或实物成功。

### BB-R8 — 报告与公开边界

- 生成按任务、类别和总体聚合的基线报告，同时保留 run-level 原始证据链接。
- 核心分母固定为全部已计划运行；基础设施失败、超时、模型拒绝、预算耗尽和工具失败
  均按真实状态公开，不能静默重跑后丢弃。
- README 公开展示至少一个成功案例和多个典型失败案例，明确样本量、模型/环境、
  评审覆盖率、实物覆盖率、未知项和能力边界。
- 首轮 campaign 封存前不公开 holdout 内容；封存后 README 和公开数据必须同时发布
  冻结 corpus、参考答案、全部计划 run 的结果及 `sealed_holdout_baseline` 标识。后续
  公共复测与首轮盲测分开展示。
- 现有错误注入 benchmark 继续作为验证器回归测试；BoardBench 使用独立名称和数据
  schema，避免把检测器准确率与端到端板卡成功率混为一谈。

### BB-R9 — 主分支与范围约束

- 修复主分支测试、文档和发布检查中对已删除文件的引用；最终以真实运行的测试与
  `scripts/release-check.sh` 结果为准，不以静态检查代替发布门禁。
- 本任务允许为采集、评分、报告和暴露根因所必需的最小产品修复；不以新增模型供应商、
  重写 Agent 框架、扩展安装器或增加无关 PCB 操作为交付目标。
- 发现产品缺陷时必须先由 BoardBench 证据定位到失败类别，再单独修复并保留修复前后
  run；不得为提高数字而修改参考答案或删除困难任务。

## Acceptance Criteria

- [ ] BB-AC1：BoardBench v1 含 20 个冻结任务，五类各 4 个；每个任务都有自然语言
  prompt、机器可读参考答案、人工 review rubric、版本、hash 和许可信息；首轮运行前
  holdout 不在 Agent 权限或公开源码内，封存后完整公开。（BB-R1）
- [ ] BB-AC2：至少 60 个互相隔离的真实模型 run 从自然语言进入默认 Agent 产品路径；
  每个任务至少 3 次，全部使用 campaign 开始时冻结的同一默认模型/配置，且没有 run
  直接输入预制 `CircuitPlan`/IR/KiCad 工程。（BB-R2）
- [ ] BB-AC3：60 个 run 都有可校验 manifest、原始 trace、工程或失败产物、自动评分、
  usage/cost 状态、工具次数和终止原因；缺失证据不被计为通过。（BB-R3、BB-R4）
- [ ] BB-AC4：自动评分覆盖完整 KiCad 工程、真实库解析、参考网络、ERC、DRC、必需
  电路、额定约束和 false-completion，且评分器有针对 clean/fault fixtures 的测试。
  （BB-R4）
- [ ] BB-AC5：60 个计划 run 都有结构化人工记录；可审查结果包含功能结论、修改计数、
  主动工作分钟、三态 diff 和非 ERC/DRC 问题，未产出原理图者保留可核验的
  `not_applicable` 原因；v1 发布时没有 `not_reviewed`。（BB-R3、BB-R5）
- [ ] BB-AC6：每个失败 run 都使用七类 primary stage 之一并记录正交 cause/owner；
  campaign 期间的自动建议、人工最终分类、超时和基础设施失败全部保留，v1 发布时没有
  `unclassified`。（BB-R6、BB-R8）
- [ ] BB-AC7：至少 5 块板已真实下单、装配并上电，且五类各至少 1 块；每块都有
  可制造性、焊接、首上电短路、电源轨、下载、核心功能和修订版数的可追溯证据。
  （BB-R7）
- [ ] BB-AC8：主分支全量测试与 `scripts/release-check.sh` 在记录的验收环境真实通过，
  不再引用已删除的文件；未执行或外部受阻的检查不得写成通过。（BB-R9）
- [ ] BB-AC9：README 同时公开基线方法、成功案例、典型失败、样本/模型/环境、人工与
  实物覆盖率以及能力边界，不以目标成功率替代观测结果。（BB-R8）
- [ ] BB-AC10：至少能够从报告直接回答三项结果：不改原理图通过工程师审查的板卡数/
  比例、被制造板卡第一次上电工作的数量/比例，以及每类失败的数量与责任归因。
  （BB-R5、BB-R6、BB-R7、BB-R8）

## Out of Scope

- 为了提高 BoardBench 数字而新增更多模型供应商或建立模型竞技榜。
- 大规模重写 Hermes/Agent 框架、安装器或 PCB 工具表面。
- 把 ERC/DRC 通过解释成电气、热、EMC、法规、可制造或量产正确。
- 在 BoardBench v1 中追求预先设定的成功率、隐藏失败或只发布挑选后的最佳 run。
- 自动替代有资质工程师的设计签字、板厂下单决策或实验室安全流程。
- 将 20 个任务做成按器件名称触发的特殊生成分支。
